# IDS Project

A small Python lab project for generating web application traffic and exercising an intrusion detection setup. It contains an HTTP test runner, a record-transfer simulator, and the test case definitions used by the runner.

> Run these scripts only against systems you own or are explicitly authorized to test, in an isolated lab environment. The SQL injection strings are test inputs, and the record-transfer script copies records from the configured source to the configured receiver.

## Project structure

```text
idsProject/
├── attackSimulator/
│   ├── Sql_injection_bot.py  # Sends normal and SQL injection login requests
│   ├── malwareSimulator.py   # Pages through source records and posts them to a receiver
│   └── testCases.py          # HTTP cases imported by Sql_injection_bot.py
├── data/
│   └── test_results.csv      # Generated by the HTTP test runner; ignored by Git
└── readme.md
```

## Requirements

- Python 3.8 or newer
- The `requests` package
- A reachable, authorized lab web application implementing the routes used by the selected simulator

Install the dependency in your environment:

```bash
python -m pip install requests
```

## Configure the lab endpoints

Before running either script, edit the endpoint constants near the top of the relevant file:

- `attackSimulator/Sql_injection_bot.py`: `TARGET` is the web application base URL. The script requires HTTP and port `3000`, and validates that the host is `localhost` or a private IPv4 address.
- `attackSimulator/malwareSimulator.py`: `TARGET_URL` is the source service on port `3000`; `RECEIVER_URL` is the receiving service on port `4000`.

Use lab addresses that are reachable from the machine running the scripts. The malware simulator does not perform the same target validation as the HTTP test runner, so verify both endpoints before executing it.

## Run the HTTP test suite

From the project root:

```bash
python attackSimulator/Sql_injection_bot.py
```

The runner sends the cases in `testCases.py` sequentially with a one-second pause between requests and a 10-second request timeout. The cases cover basic GET requests, ordinary login attempts, and SQL injection strings submitted to `/rest/user/login`.

Results are printed to the terminal and written to `data/test_results.csv`. Each run replaces the previous CSV. The output contains the case ID, UTC timestamp, category, method, path, HTTP status, response time, and any connection error. It records transport/status information; it does not determine whether the application or an IDS correctly detected an attack.

## Run the record-transfer simulator

From the project root:

```bash
python attackSimulator/malwareSimulator.py
```

The script requests `/api/records` from the source in pages of 100, then posts each non-empty page to `/api/received` on the receiver. It stops when the source returns an empty page. Both services must expose those routes and return the expected JSON shape: the source response must include a `data` array. The receiver response is printed after each successful post.

## Notes

- The repository does not include the target application or receiver service; these must be running separately.
- `data/` is excluded by the root `.gitignore`, so generated results are not tracked by Git.
- `attackSimulator/testCases.py` is a Python module imported directly by the HTTP runner; run the script from the project root as shown above.
